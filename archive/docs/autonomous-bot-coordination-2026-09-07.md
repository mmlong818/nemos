# 自主 Bot 协作：核实结果与实现决策

日期：2026-09-07。状态：研究核实与架构决策；本文件不代表自主协作已上线。

## 一、Grok Bot 有什么

官方设计文章明确描述协调 Bot、Bot 间消息与工作交接；群聊承载项目共同上下文，角色记忆保持独立，Tools/Skills 为账号级能力。文章也描述协调者处理日常路由，仅遇到需要判断的决定才询问用户。

来源：https://x.ai/news/designing-grok-bot ，Organizing intelligence / The shape of information 两节。

官方实践指南描述 Projects Manager + Project Ops skill：使用项目频道和任务数据库，优先复用既有 Bot，提出团队名单，缺少专家时经用户同意才创建；专家执行任务，遇阻更新状态并联系用户。指南明确称此为实验性实践，不是任意目标可靠自动组队的保证。

来源：https://x.ai/bot/guides/how-i-run-multiple-teams-of-grok-bots 。

本机历史证据复核：工作区 outputs/grok-market-2026-09-06/downloads/projects-manager-public-template-preview.json。公开模板有 1 个 Project Ops 技能，Notion、Slack 依赖；按任务空闲状态认领，更新负责人/进度，受阻记录准确问题。其“先查询、再写负责人”规程不能证明底层有原子领取，也不能据此断言 Grok 服务端没有保障。

本轮没有重新运行 Grok 实机多 Bot 协作、没有创建 Bot 或连接第三方账号。服务端源码、具体路由算法、锁/租约、调度恢复与预算实现未取得，不能当作已验证事实。

## 二、需要纠正的产品定义

- 主助理：唯一主要委托入口，负责理解目标、组织执行、归纳结果和请求必要决定。
- Bot：执行角色，包含职责、可用技能和工具、运行状态、上下文边界。不是提示词的同义词。
- Skill：可复用的操作方法/执行规范，不自带独立运行身份、记忆或调度能力。
- 工具：实际执行检索、解析、生成、外部动作的受管接口。

当前已迁移的规则模板继续作为规则模板，不通过改名宣称它已成为具备完整自主运行环境的 Bot。现有数据、规则和接口 ID 不删改。

## 三、小丑鱼现状（源码核实）

assistant-team-routing.ts：local-name-match-v1 根据名称/关键词选至多一个执行者；目标明确要求核验时再选核验者。不是语义规划器。

assistant-team.ts：手动选择最多两个执行者，按固定顺序执行，核验与最终汇总读取已返回成果；任务范围共享、工具关闭、无私人记忆召回。有回执、输入哈希校验、超时、取消、恢复复用基础。

专业执行技能仍通过准备页独立运行。最近的附件转交解决输入搬运，不解决统一任务 ID、多技能依赖或自主重规划。

## 四、采用的架构方向（小丑鱼设计，不声称复制 Grok 内部实现）

一个主任务拥有计划修订、子步骤、共享材料引用、成果引用和回执。主助理先判断是否有必要拆分；简单任务独立完成。复杂任务从已启用、可用且已授权的角色和执行技能中提出有依赖的计划。

模型提出计划，服务端校验后才能执行：

1. 步骤 ID 唯一；依赖存在且无环；执行者、技能和工具均在当前用户的允许列表。
2. 每一步明确目标、输入引用、输出要求及验收条件。缺少必要能力时标记阻塞，不伪造技能、不悄悄用文字替代要求的真实文件。
3. 独立步骤可有限并行；依赖步骤必须等待成功回执。下游只得到其依赖的材料和成果，不获取其他 Bot 私有记忆。
4. 队列持久化、原子领取、租约/过期回收、幂等提交；重启从未完成步骤恢复，不重复执行已经确认的外部动作。
5. 明确调用数、并发数、时间和累计 token 上限；有限次修订。模型建议不能扩大授权或预算。金额估算与实际收费分开，不把 token 上限称为硬金额上限。
6. 核验不通过时保留原因，有限返工；失败不能被汇总阶段改写成成功。
7. 新建/安装角色和工具、外部发送/发布/删除以及需要扩大预算的行为必须走确认；对已授权范围内的低风险步骤可自动运行。

复用既有 AgentJobQueue/Worker 和回执机制，不为此恢复开发引擎，不引入必须依赖 Notion/Slack 的第二套任务数据库。

## 五、界面约束

用户只描述目标并添加材料，手选 Bot 非必要。不新增团队调度主页面或重复抬头。

当前任务内按需展开“执行安排”：显示步骤、执行角色、状态、当前阻塞和预计调用上限；默认聚焦进度、待决定事项及最终成果。用户可暂停、修改计划或改为独立完成。多 Bot 内部往返不作为多条普通聊天刷屏。

示例：资料整理 → 方案比较 → 演示生成 → 交付核验。四步归属于同一个任务；不是四个页面让用户逐个点击。

## 六、实施顺序与验收门槛

1. 统一主任务/子步骤契约、依赖校验和执行器适配；保留旧任务读取与重试。
2. 有界规划器与现有队列接入，允许自动选人/选技能，服务端验证后执行。
3. 材料/成果按引用交接；任务页投影计划、阻塞、完成与批准状态。
4. 隔离测试后做合成资料真实模型验收，按授权预算运行。

必须覆盖：不拆分的简单任务；多个技能串联；独立步骤并行；循环依赖/虚构技能拒绝；停用角色与权限变化；附件缺失或读取失败；同一任务重复提交；阶段超时/取消；重启恢复不重复外部动作；超预算停止；核验失败返工上限；材料中嵌入“调用工具”不提升权限；导出/删除/外发的批准边界。

本轮完成研究与架构取舍，未改变线上自动分派行为，未调用付费模型。
