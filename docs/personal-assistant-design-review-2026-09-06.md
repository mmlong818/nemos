# 小丑鱼：个人 AI 助理设计与可行性评审

日期：2026-09-06  
评审对象：当前本地工作树，应用版本 0.2.3；包含尚未提交的开发能力移除、客户端和多模型改动。  
评审目标：判断项目能否成为用户个人长期使用的、极其优秀的 AI 助理。

实施进展：评审后的调整见[可靠性记录](personal-assistant-reliability-2026-09-06.md)、[模型连接与任务选模](personal-assistant-model-readiness-2026-09-06.md)、[Buzz 选择性采用](buzz-adoption-validation-2026-09-06.md)和[记忆证据接入及当前剩余事项](personal-assistant-memory-evidence-2026-09-06.md)。以下内容保留评审当时的发现，不能把其中所有问题视为当前仍未处理。

## 一、结论

后续实施：用户同意参考 Grok Bot 模式后，新增了[主助理与专职 Bot 的第一批改造](assistant-team-adoption-2026-09-06.md)，沿用本评审的个人助理目标与安全边界。

**可以沿用现有基础实现，但当前尚不能认定已达到这一目标。**

当前项目已经有实质性的记忆、执行、文件交付与安全基础，不是只有聊天界面的原型。主要欠缺是把这些基础组织成“持续理解用户、维护正在推进的事情、可靠执行、主动跟进、验证结果”的完整循环。

现有设计更接近“拥有多种能力的 AI 工作应用”。个人助理还需要一个贯穿所有入口的工作状态：用户当前在意什么、有哪些承诺未完成、下一步是什么、何时需要提醒、哪些事需要再次授权。

建议沿用现有客户端、记忆内核和 Agent 运行时，先补可靠性与个人工作连续性；不必为了这个目标恢复已移除的开发引擎，也不应先扩张能力数量。

本轮只做检查与评审，未修改业务代码、个人数据或远端仓库。

## 二、将核心目标变成可验收的行为

建议产品目标写成：

> 让小丑鱼持续理解我的偏好和正在推进的事情，在我授权的范围内完成工作，记住承诺、主动跟进，并给我可验证的结果；遇到不确定、失败或权限边界时如实说明。

“优秀”不是能力卡片的数量，而是以下行为稳定发生：

1. **懂我**：记得经过确认的偏好、背景与约束，知道哪些事实已变化；不用每次重新交代。
2. **接得上**：隔天、重启或切换模型后能接着做；不同任务的敏感内容不会误串。
3. **办得成**：能读取需要的资料、调用合适的工具、处理失败并交付成果，而不只是提出建议。
4. **跟得住**：知道未完成事项、截止时间和等待条件，在约定时间跟进，不靠用户反复询问。
5. **值得信任**：重要结论有来源；不能执行时不会声称已完成；高影响操作先确认。
6. **越用越顺手**：从用户明确的采纳、纠正和拒绝中改进做事方式，用户可以查看、撤回这些学习结果。

可实现边界：本机运行、明确授权和已接通服务范围内的个人助理可以作为目标。关机后继续执行需要额外的常驻执行环境；任意网站都能操作、完全无需人工确认、永不出错，都不应作为产品承诺。

## 三、现有能力与目标的差距

| 目标能力 | 当前证据 | 判断与缺口 |
| --- | --- | --- |
| 长期记忆 | 实际接入 `nemos-memory`；有归档、派生记忆、反思、失效和领域检索配置 | 基础可复用；任务事实如何进入长期记忆、来源与不确定性如何展示，还未形成完整产品流程 |
| 跨天任务连续性 | 有任务、运行、检查点、产物索引与交付回执 | 已有执行状态持久化，但网页会话的近期上下文恢复存在已复现缺口；两者不能混为一谈 |
| 文件与办公交付 | 有真实文件生成、转换、版本管理、结构检查与可编辑副本 | 是现有强项；结构合格不能证明事实正确、内容优质或版式适合用户 |
| 工具执行与授权 | 有工具网关、审批、取消、任务队列、重试和不确定交付状态 | 有可靠执行基础；还需要围绕真实个人任务验证完整成功率及权限边界 |
| 搜索与外部账号 | 有搜索、浏览器和扩展/OAuth 接入框架 | 必须区分框架存在、插件启用、账号连接、真实调用成功；内置 EML/ICS 解析不等于在线邮箱和日历 |
| 主动跟进 | 有固定任务与按时间、轮次触发的执行入口 | 当前时间触发依赖页面轮询；缺少独立可靠的调度和围绕承诺的跟进流程 |
| 多模型使用 | 有模型目录、默认选择与任务指定模型路径 | 当前是单个服务连接下的多个模型，不是同时保留多套服务/key；可见模型不等于适合执行当前任务 |
| 个人化与学习 | 有称呼、关系档案、记忆检索和交付偏好 | 不能说没有个人化；但仍缺少统一管理长期目标、进行中事项、决定及下一步的个人工作状态 |

## 四、优先处理的问题

### P0-1：同一网页会话在重建引擎后失去近期上下文

**证据等级：代码确认，并通过内存存储、模拟模型复现。**

`engine.ts` 的 `ensureRecentHistory`（约 640 行）在收到 `sessionId` 且缓存为空时直接建立空数组并返回，没有从持久化记录恢复该会话。网页请求会携带 `sessionId`。

`server.ts` 的 `rebuildLLM`（约 982 行）在保存模型连接时重新创建引擎，所以该问题不只与应用重启有关。

本轮复现：

1. 创建内存记忆库与模拟模型，不访问真实模型服务。
2. 在同一 `sessionId` 下发送一个唯一事实，采用任务使用的 `archive-only` 写入模式。
3. 同一引擎再次发送“继续”，检查模型收到的用户上下文。
4. 保留同一记忆库、重建引擎，再以同一 `sessionId` 发送“继续”。

结果：

```json
{
  "sameSessionBeforeRebuildHasDetail": true,
  "sameSessionAfterRebuildHasDetail": false,
  "afterRebuildUserPrompt": "对方：继续"
}
```

这证明的是近期上下文没有恢复，不是数据库被删除，也不代表所有长期记忆全部失效。界面能显示旧消息，同样不等于模型本轮拿到了旧消息。

建议：以真实 conversation/session 标识持久化和恢复对话；为长会话保存可追溯摘要及任务状态。不能以恢复同一角色的所有历史来修补，否则会破坏会话隔离。

### P0-2：定时任务依赖聊天页面轮询

**证据等级：静态调用链确认；本轮未做真实时间调度压测。**

`web/index.html` 的 `pollCapabilityTasks` 调用 `/api/capabilities/due`，页面每 60 秒调用一次。`server.ts` 的该 GET 路由才调用 `enqueueDueCapabilityTasks("time")`。

当前检查范围内，没有发现服务启动时独立调用时间调度的循环。后台 worker 会执行已经排入的任务，但“发现到期任务并入队”仍由页面请求驱动。

影响：没有该页面轮询时，不能保证到点入队；页面计时器被节流时也可能延迟。客户端最小化到托盘与完全退出要分别验收，不能笼统声称关闭窗口也会准时执行。

建议：把到期检查放到后端调度器，页面只读状态；补一次性提醒、重启补偿、休眠唤醒、多窗口去重和明确的漏跑策略。保持用户授权要求。

### P0-3：模型目录发现不等于任务能力验证

**证据等级：代码确认；未调用真实 key 验证服务商兼容性。**

`model-connection.ts` 按返回的 `created` 降序排序；无时间信息时保留服务端返回顺序，并用名称正则过滤非聊天模型。连接验证仅进行一次短文本、非流式、无工具的请求。

当前机制无法证明“最新模型”支持应用需要的流式输出、工具调用、结构化输出或图片理解，也不能确认无时间戳的列表顺序代表新旧。日常模型还可能来自固定预设，而不是当前 key 可用的目录。

建议：保留用户要求的“最新优先”，定义为“在当前账号可用、满足任务能力的模型中优先较新版本”。保存用户手动选择；缺少时间信息时说明无法判断；列表接口不可用时保留手动配置途径。模型、搜索、语音、图像服务分别记录可用性，避免换聊天模型后其它能力悄然变化。

### P1-1：有记忆内核，但缺少完整的个人工作记忆流程

`conversationMemoryWriteMode` 对任务模式和附件输入采用 `archive-only`。这是避免把材料、案例或虚构内容误记成用户事实的有意保护，应保留。

缺口是没有与之配套的统一流程，把用户确认的决定、偏好变化、截止时间和未完成承诺沉淀为个人工作状态。不能简单把所有任务材料自动抽取为用户记忆来解决。

另外，`recallUserFacts` 从记忆包提取文字/摘录后传给模型，没有在这条路径充分保留来源、置信度等信息；专业能力的偏好注入则只选少量明确的交付习惯。这些边界适合防污染，但不足以让助理掌握一件事的完整来龙去脉。

建议明确区分：用户事实、用户偏好、任务决定、外部资料、助理推断、助理承诺。为长期使用补“从哪里得知、何时确认、何时失效、如何纠正/撤回”。在现有任务/运行/产物结构之上添加长期事项，不另造一套重复的执行系统。

### P1-2：能力就绪状态存在失真路径

**证据等级：代码确认，并通过纯函数复现。**

`product-platform.ts` 的 `platformConnectorStatuses` 通过扩展名称/能力关键词匹配，再以 `enabled` 判断 ready；这条路径不检查 `providerAttached` 或运行错误。服务器其它扩展状态路径则检查这些字段，存在口径不一致。

传入一个 `enabled: true`、`providerAttached: false` 且带运行错误的 GitHub 扩展描述，结果仍为 `ready`。这证明判断函数可能误报，不表示当前用户实际安装的插件已处于该故障状态。

建议统一为：未安装 → 已安装 → 已授权 → 已连接 → 实测可用；保留最后检查时间和失败原因。助理必须按真实就绪状态决定能做什么。

### P1-3：助理定位与旧陪伴提示存在冲突

普通 `send/sendStream` 路径仍使用包含角色生活、亲密互动和“不渲染 Markdown”的旧陪伴提示；专门的工作通知路径另有强调交付、来源与 Markdown 的提示。

建议统一助理原则，按任务调整表达方式。温暖、有个性可以保留，但应以真实、可靠、推进用户目标为先，不需要通过虚构自身现实生活支撑连续感。不要让不同入口给同一个助理施加互相矛盾的工作要求。

### P1-4：测试通过尚不能证明“个人助理优秀”

本轮实际执行：

- `npm run typecheck`：通过。
- `npm test`：共 382 项，381 通过、0 失败、1 跳过；跳过项为真实 Blender 三维检查。
- 两项额外只读诊断：复现会话重建后近期上下文缺失、断开的扩展仍报告 ready。

现有测试有真实文件和状态持久化检查，也有模拟模型与源码字符串断言。`capability-real-quality.mjs` 有真实服务调用路径，但不少质量条件仍是关键词、文件和检查回执；不能仅凭这些条件推断内容事实正确、体验优秀。

本轮未进行真实付费模型、用户账号服务、打包客户端界面回归、跨天提醒或最终办公文件视觉验收。上述通过结果不是新客户端可直接发给他人的发布结论。

## 五、建议的改造顺序

### 第一阶段：先让已经承诺的功能可靠

- 修复同一会话的恢复与隔离。
- 将定时任务触发移到后端，验证最小化、退出、重启与唤醒边界。
- 完善模型可用性、任务能力探测和错误说明。
- 统一连接器与能力就绪口径。
- 把本次复现与真实使用场景加入回归。

阶段完成条件：不增加新能力，也能连续使用已有功能；核心失败能定位、恢复，界面状态与实际执行一致。

### 第二阶段：围绕用户的长期事项组织工作

在已有任务系统上增加个人事项状态：目标、当前阶段、下一步、截止时间、依赖、等待谁、授权范围、关联资料和结果。

让同一个助理能够回答：“我最近最重要的事是什么？”“上次决定了什么？”“这件事现在卡在哪里？”“今天需要我确认什么？”

保留会话和资料的隐私边界；跨任务汇总应有明确规则，而不是把所有历史无差别塞进提示词。

### 第三阶段：接通实际需要的工作环境

先从用户真实使用的 1–2 个服务或目录开始，按具体任务验证读取、检索、授权、操作、回执与恢复。不预设用户一定使用某种邮箱、日历或办公平台，也不以插件数量作为目标。

把“每日简报、约定提醒、等待事项检查”做成真正可用的工作流；是否需要关机后执行及远程常驻服务，另行由用户决定。

### 第四阶段：通过反馈形成可控的个性化

先稳定少量高频任务：研究摘要、资料整理、文档交付、决策辅助、事项跟进。把用户认可的格式、取舍和流程保存为可检查、可撤回的偏好与技能。

不以不受控的“自主进化”、无限多角色或新增大型引擎替代质量改进。

## 六、建议的个人验收集

以下是下一阶段的验收建议，不是本轮已经达到的指标。

| 场景 | 应观察到的结果 |
| --- | --- |
| 上周说明偏好，本周提出相关任务 | 合理使用偏好；能解释来源；无关任务不硬套 |
| 明确纠正一个事实 | 后续使用新事实，旧事实不再作为当前真相；可追溯纠正 |
| 上传含第三人称信息的材料 | 不把材料里的经历记成用户经历 |
| 重启后在同一任务说“继续” | 保留目标、关键决定、附件关联和下一步 |
| 新开一个无关任务 | 不把其它任务的原始对话误当成刚才讨论 |
| 保存模型配置或切换模型后继续 | 任务状态与历史保持连续；不重复执行外部操作 |
| 最小化后到达提醒时间 | 后端准时入队；结果通知可见且不重复 |
| 休眠、断网、重启后恢复 | 清楚标记漏跑/失败并按既定规则处理，不假装已执行 |
| 调用未连接或过期授权的服务 | 正确提示缺少什么，不报告已经连接或完成 |
| 要求发送、删除、支付等重要操作 | 严格遵守授权；操作和结果留有记录 |
| 提出研究与文件交付任务 | 来源、结论、文件内容、可打开性和视觉质量分别核验 |
| 查询未完成事项 | 汇总真实事项、等待条件和下一步，区分建议与已承诺行动 |

可从 20 个用户实际会做的代表任务开始，连续进行至少一周的小规模使用。建议首轮目标：至少 18 个按事先约定的标准完成；越权操作、虚报完成和严重跨会话记忆污染必须为零。此门槛只用于发现并约束问题，不代表覆盖所有场景或统计上的可靠性证明。

## 七、设计资料一致性

README 标注应用 0.2.3、23 项能力；ROADMAP 仍写 0.2.19 Alpha，部分设计文件仍有已经移除的开发能力及旧能力数。历史验收数字也不等于当前测试结果。

建议下一次设计更新时明确“现有事实、目标设计、已废弃内容”，把本报告的个人助理目标作为主线，避免继续按旧平台化范围扩张。
