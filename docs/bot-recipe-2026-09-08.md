# Bot 配方与同意门（2026-09-08）

市场模板此前只能携带一段工作规则（`tools: "off"`、`memory: "task-only"`、不带定时任务）。锁得很死所以安全，代价是"配方"能力整体不存在。本轮补上两类可携带内容与一道结构性的同意门。

实现见 [`bot-recipe.ts`](../sdk/typescript/examples/companion/bot-recipe.ts)、[`assistant-team.ts`](../sdk/typescript/examples/companion/assistant-team.ts) 的 `importTemplate`，以及 [`bot-market.ts`](../sdk/typescript/examples/companion/bot-market.ts) 的 `recipe` 字段。

## 一、配方能带什么

| 类型 | 落到哪 | 硬约束 |
| --- | --- | --- |
| 技能（可复用流程） | 技能库，走与其它安装技能相同的 `installSkill` 准入检查 | 必须写清"何时使用"；正文是 Markdown 流程 |
| 定时任务 | 计划面板 | **恒建成暂停**；只允许按天或按轮次触发；必须指向宿主真实存在的能力 |

### 配方里没有「记忆」

参考实现的模板会携带记忆条目，导入时以低可信层写进去。小丑鱼不这么做，原因不是更谨慎，而是模型不同：

- 市场 Bot 以 `memory: "task-only"` 运行，本来就读不到用户记忆，携带记忆没有消费方；
- 模板作者预填的"记忆"实际上是他对用户的断言。小丑鱼的记忆有完整的主体归属（`subject_id` / `subject_resolution` / `perspectives_conflict`），把第三方断言写进用户事实层就是身份污染——这正是产品承诺里「不携带外部 Bot 的私人记忆」要挡的东西。

用户自己的偏好由记忆页的显式录入路径负责，不经由模板。

## 二、同意门为什么是结构约束而不是提示词约束

参考实现靠提示词让模型「先弹问询卡、且不能同一轮安装」，并且是由 Bot 自己调 `update_state` 把配方装进去的。那是软约束：模型不听话就失效。

小丑鱼把它换成硬约束，共三层：

1. **模板本身没有任何工具权限**，从头到尾都不能写状态。配方由宿主在用户操作下应用，所以「从正文读到指令就去安装」这条路根本不存在，不需要靠规则去堵。
2. **同意令牌只在预览接口发放**。`GET /api/assistant-team/template-recipe` 是唯一发放点，也是唯一不改变任何状态的一步。客户端拿不到令牌就装不了任何配方内容——"先看过再决定"因此是结构保证，而不是界面顺序。
3. **确认与落地必然分属两次请求**。预览拿令牌，导入带令牌，两步之间没有捷径。

令牌绑的是模板身份 **加上归一化后的配方内容**，不只绑版本号：只绑版本号的话，同一版本内容被换掉就能拿旧令牌落地新内容。

四种拒绝：

| 情形 | 结果 |
| --- | --- |
| 没有同意信息 | **不报错**，Bot 照样建立，配方一项都不落地 |
| 有勾选但没有令牌 | 428，提示先查看内容 |
| 令牌不匹配 | 409，提示内容已变化需重新查看 |
| 勾选了配方里没有的标识 | 400，挡的是客户端塞入没展示过的条目 |

第一条是刻意的：同意门守的是配方，不是添加 Bot 本身。一个不带令牌的普通添加应当照样拿到 Bot，默认结果是最保守的那个（什么都不装），而不是一条错误——把它做成报错会逼所有入口都先走预览，而真正需要守的只有"装东西"这一步。

## 三、落地时的不变量

- **定时任务恒 `enabled: false`**，不看配方里怎么写。配方能自带一个会自己跑起来的任务是不可接受的；`permissions.automaticRoutines` 仍是 `false` 且不因携带配方而改变。新装的任务由用户在计划面板显式打开，随后归第 [失败注册表那一轮](failure-registry-2026-09-08.md) 的"结果无人查看则自动暂停"管辖。
- **逐条独立处理**。一条技能没过准入检查不该让其余条目连带失败，也不该把整次导入回滚成"什么都没有"——用户已明确同意的其它条目应当生效，失败的那条在收据里说明原因。
- **顺序是先落 Bot 记录、再落配方**。落地要写磁盘（技能文件、任务文件），这不在 SQLite 事务范围内；放进事务的话，一次安装失败会回滚 Bot 记录，但已写入磁盘的技能文件回不来，用户会得到"Bot 没了但技能还在"的状态。
- **重复添加不重装配方**。已有的 Bot 说明上次已经问过一轮，再装一遍会产生重复任务。
- **收据不可由请求体改写**。`recipeReceipt` 记录装了什么、装到哪、哪些没采纳，编辑 Bot 的名称或规则不会把它清掉——只在导入时弹一次对话框的话，第二天就没人记得这个 Bot 往本机装过什么。

## 四、目录内容

目前只有 `project-guide`（项目推进助理）带配方，作为端到端的真实样本：一个技能（阻塞升级判断）和一个定时任务（待决事项汇总）。

定时任务用**按轮次**触发而不是按天：按天触发时没有当轮对话材料，一个 `tools: "off"` 的 Bot 只能产出一个"请提供材料"的空壳。这也是判断某个模板该不该带定时任务的标准——只有当承接能力能自己取到输入，或者触发方式本身带来上下文时，定时任务才有意义。其余 7 个模板暂不带配方，等各自确有需要时再加。

## 五、界面现状

**已做**：Bot 详情抽屉里新增「这个 Bot 装了什么」区块，逐条列出落地位置与状态（定时任务显示"已添加 · 暂停中"）、失败原因，以及用户当时没有勾选的项数，并写明内容来自模板作者、仍按未经核实处理。收据此前只存不显示，只在导入时弹一次对话框的话第二天就没人记得了。

**没做，且不应由本轮做**：预览与勾选的对话框。原因是 2026-09-07 的[官方市场与现有 Bot 分离](official-market-separation-2026-09-07.md)已按要求清空市场页面、删除卡片渲染、搜索筛选、导入详情和添加按钮，8 个模板改为一次性服务端导入到技能库。因此 `/api/assistant-team/import` 目前没有客户端调用方，同意门的对话框也无处安放——在市场页重建入口等于反转那次决定。

这不影响同意门的有效性：它守的是导入路径本身，无论调用方是界面、脚本还是运维操作。官方市场开放时，预览接口返回的 `notes` 字段已经带上了要展示给用户的三句话。

## 六、暂缓

- **用户自建 Bot 导出配方**：现在配方只能随应用发布的目录携带。让用户把自己调好的技能与任务打包成可分享的配方，需要先决定分享边界（本机文件、还是经由同步服务），与声明式沙箱那一轮相关。
