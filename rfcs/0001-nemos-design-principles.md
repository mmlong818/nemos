# Summary

本 RFC 定义 Nemos Memory SDK 的基础设计原则。后续架构变化应说明与这些原则的兼容关系；需要改变原则时，应通过新的 RFC、迁移方案和测试记录完成。

# Motivation

长期记忆涉及用户事实、模型推断、时间变化、隐私和数据生命周期。若没有稳定原则，不同功能容易对同一内容采用不一致的写入、检索和删除规则。

这些原则用于统一数据模型、公开接口、测试和产品行为。

# Principles

## 原则 1：来源清晰，用户保持控制

用户陈述、模型推断和外部资料必须保留不同来源标记。模型生成内容不能被标记为用户权威事实。

工程要求：

- 每条记录保留来源和权威性；
- 派生内容标记为 `derived`；
- 用户可以查看、纠正或删除允许操作的记忆；
- 高影响写入遵循明确权限边界。

## 原则 2：按用途分层

episodic、semantic、personal-semantic、procedural 和 archival 使用不同的写入、检索和生命周期规则。

分层的目的不是增加概念数量，而是避免把经历、公共事实、个人事实、习惯和原始记录混入同一检索通道。

## 原则 3：原始记录与派生解释分离

原始事件保持可追溯。摘要、事实、习惯和其他派生内容以独立记录存在，并通过证据关系指回来源。

纠正不会静默覆盖历史，而是产生新的状态和关系。

## 原则 4：衰减、失效和删除是不同操作

- **衰减**：降低召回优先级；
- **失效**：事实曾经有效，但当前不再有效；
- **删除**：按授权移除数据；
- **归档**：保留原始记录用于追溯。

接口和产品文案不能混用这些语义。

## 原则 5：用户与租户隔离

所有存储和检索操作必须明确 tenant、user 和必要的 scope。客户端提交的标识不能直接作为可信身份。

跨用户读取、写入、反思和失效操作默认拒绝。

## 原则 6：本机优先，网络边界明确

默认实现使用本机存储。调用外部模型、联网来源或第三方工具时，应用需要明确发送哪些数据、发送给谁以及使用何种权限。

本机优先不等于完全离线；网络行为应由功能和用户配置决定。

## 原则 7：数据可导出

用户数据应使用稳定、可审查的结构导出。导出需要保留内容、来源、时间、关系和必要校验信息，避免只能依赖单一应用读取。

当前实现提供 JSON-LD 与 Markdown 导出。

## 原则 8：声明必须有实现证据

公开能力、性能、安全和兼容性声明应由代码、测试或可复现结果支持。

设计目标不能直接写成已实现功能；评测结果也不能脱离对应版本、模型和数据配置进行外推。

# Consequences

这些原则会带来额外的数据结构、测试和迁移成本，但可以降低以下风险：

- 模型推断污染用户事实；
- 不同用户之间的数据越权；
- 过期事实继续参与回复；
- 删除、失效和归档语义混乱；
- 文档承诺超过实际实现；
- 用户数据被单一应用锁定。

# Alternatives

## 使用单一记忆表和统一检索

实现更简单，但难以表达不同来源、权威性和生命周期。当前不采用。

## 只保存摘要，不保存来源关系

存储更少，但无法可靠纠正、审计或重新提取。当前不采用。

## 由应用自行处理用户隔离

会让安全边界分散到每个集成点。Nemos 仍要求在 SDK 使用方式和存储键中明确隔离。

# Compatibility

现有接口应优先保持向后兼容。破坏性 Schema 或公开 API 变化需要：

1. RFC 记录；
2. 明确迁移路径；
3. 兼容性和数据完整性测试；
4. README、类型和示例同步更新。
